# 程序化 SOP 质量合同

## 何时使用

当任务开放式、依赖真实世界参考、包含多个相互连接的部件、要求可调资产，或“高质量/细节丰富”
会显著改变建模路径时使用。用户已经提供精确 recipe 的小修改、抽象造型探索和一次性可逆 probe
不必机械填写完整合同，但仍保留相关完成门。

## 最小合同

复杂产品可用`houdini_product(action="schema")`读取格式，再define会话需求记录，帮助连续修改时保留要求与证据。`productMode`只提供领域工作提示；模型按任务需要选择记录与检查，代码执行、任务提交和保存不要求先登记数量、尺寸或计划。结构化保存用`houdini_exec(checkpoint={expected_path:已命名HIP})`，与code/allow_raw互斥。
先用`houdini_query(source_ref="index")`列来源、按引用回读原文；定义只引用当前session的用户材料或澄清回答。
define必须直接调用Host工具，Code Mode/PTC嵌套写入会拒绝；schema/read/review可用于嵌套读取。
下表是提取要求的检查角度，不是第二份可写核验表；将相关内容放入定义的要求描述与假设，未知项显式保留：

| 字段 | 内容 | 可接受证据 |
|---|---|---|
| target | 对象/效果、变体、使用场景 | 用户选择、现有场景、来源明确的参考 |
| reference status | 外部参考、用户参考或明确的无参考边界 | URL/图片/规格表/用户授权的假设 |
| quality/LOD | 轮廓级、镜头级、产品级、模拟代理等 | 用户目标和最终观察距离 |
| simplifications | 哪些结构可省略，哪些关系不可破坏 | 用户确认或带风险的显式选择 |
| units/dimensions | 单位、关键尺寸、所属零件和允许范围 | 场景单位、图纸尺寸线端点、规格来源或用户给定值 |
| controls | 用户需要调整的参数、范围和依赖 | 控制节点、spare parms、HDA interface |
| anchors | 共享轴、端点、基准面、中心和局部坐标系 | 单一 detail/属性/参数源 |
| module relations | 部件之间必须满足的空间/数据关系 | 下表中的逐项检查 |
| evidence plan | 数据检查、特写视角、动画帧和停止条件 | 可执行动词/查询与明确视角 |

引用外部真实性时要记录来源；没有来源时只能报告“内部一致/基于假设”，不能升级成“符合真实范围”。
厂家照片配工程图时，描述保留图/页及标注位置、所属零件、尺寸性质、重复数和冲突；实际图片需从原材料核对，Host来源文字标记不等于像素恢复。同页裁图不是独立来源。把必需部件、尺寸、关系、控制、细节和观察要求分别列入requirements，不用固定八项上限删减义务。每条关系的每个有义务状态单独列项，例如闭合接触、半开连接、全开连接；写清对应控制值，有释放/锁止/复位要求时包含释放后的状态。建模前确定期望，不能从实际幸存件反推要求。简单编辑不强制建立完整定义。

执行检查后，按真实回执把`checks`绑定到`geo_check_interfaces`或`test_controls`的合同标识和具体检查id；控制状态中的关系另指定`baseline`或实际case id。没有结果时留空，不编造标识或作者pass。绑定输出必须是定义的最终SOP，最后相关修改后刷新证据并read覆盖；局部pass不能抵交付输出，控制响应不能抵部件连接。`measured`只表示该项有匹配且适用的历史测量，不能认证来源理解或全部产品正确。detail/visual保持数值未认证，作者另用明确部件、状态和问题的实际图像观察说明；图像送达或数字通过都不算语义识图。

对物理尺寸，在dimension要求中记录`dimension={group,axis,expected_m,tolerance_m}`；米制期望来自原图/要求而非模型当前尺寸。
对独立零件，在part要求中记录`members={group,expected_components}`，匹配最终组的真实连通件数；融合为一个实体后的特征数量须另取适用证据，不能把融合前件数当最终独立件数。
对实际接触，在relation要求中记录`contact={source_group,target_group,max_distance,expected_points}`；距离是最终SOP局部单位。不同组、少选接点、放宽容差或零相交检查都不能替代该声明。
对运动状态，用`control_values`记录必须观察的实际控制值；只有对应test_controls case的actual_values匹配才覆盖该状态。
细节要求可附`feature={family,purpose,attachment,controls,construction,inspection}`，把用途、依附关系、参数和观察方法保留为设计计划。
计划齐全仍不认证实物；非零面积、一个锚点或一起移动不能证明细节真正连接。
阶段切换和交付前调用review：workflow分别给出保存、声明计划、数值覆盖与语义复核；evidence_index给最近最终输出的精确绑定，超出部分从历史结果回读。它不自动绑定、不授权通过、不阻止保存。改动既有组/状态/尺寸/件数/接触预期会保留修订提示；说明依据并重新验证，不能让同名新阈值掩盖旧失败。

定义修订先read当前revision，用expected_revision和原因顺序提交；新增用户材料先回读再更新要求。source_refs引用具体依据；逐条核对后可用reviewed_through记录已审阅到的用户/澄清来源，不必把每条“继续”或进度询问都加入依据。该游标只表示作者确认已审阅，不证明理解正确或授权；不能为清除提醒跳过原文。删除义务须在retired保留理由与来源，来源引用本身不证明用户同意简化。发生revision冲突时read各候选、合并仍有效的义务，再按工具返回的冲突列表显式解决；压缩或续接也先read定义并复核原来源。定义、退役、摘要和历史回执都不赋予场景所有权或修改权限。todo只记录推进顺序；交付报告说明实测、未测和失败，不另建自报完成账本。
需要用户补齐合同时，先把常见且会改变路径的选择做成选项并说明影响，再允许用户用自定义文本补充；
不要把车型、LOD、交付深度和允许简化全部推给一个空白输入框。

## Anchor 与依赖

先建立尺寸和 anchor，再让模块派生：

```text
controls / reference dimensions
  → named anchors and local frames
    → module generators
      → relationship checks
        → integrated output
```

- 一个会影响多个模块的量只有一个维护位置；下游用引用、属性或表达式派生。
- 模块输出保留稳定的 `part_id/module` 等标识，便于局部统计和关系检查；标签的具体名称可按资产约定。
- 绝对坐标不是禁用项；只在它确实是局部常量且不会与其他模块重复表达同一事实时使用。
- 一次合理调参后若必须手改多个代码字符串才能恢复连接，参数化完成门失败。

## 常见模块关系

只选择任务相关的关系，不要求每个资产套满：

| 关系 | 需要证明什么 | 反例 |
|---|---|---|
| coincident axis | 两个部件共享或按偏移共享轴线 | bbox 重叠但轴向错误 |
| anchored endpoint | 端点位于命名 anchor 的容差内 | 视觉靠近但实际悬空 |
| contained/inserted | 部件进入目标范围并保留正确深度 | 全部穿透或只擦边 |
| clearance | 最小间隙在允许范围内 | 为消除一处冲突而制造另一处冲突 |
| forbidden intersection | 不允许的部件对没有相交 | “被遮住所以可接受”但合同未允许 |
| contact/grounding | 接触位置和法线符合用途 | 只用全场 bbox 推断接触 |
| symmetry/pairing | 对称或成对件共享规则且允许指定差异 | 分别硬编码后逐渐漂移 |
| attribute continuity | 下游所需属性 class/value 连续 | Merge 无 error 但属性默认化 |

现有词表不能直接给出关系时，可用只读 HOM/局部几何 probe 建立证据，并把重复出现的通用意图
记录为工具候选；不要为单个资产发明专用 verb。

## 验证阶梯

按任务目标选择需要的检查，简单修改不必执行完整阶梯。

1. **要求核对**：来源、假设、LOD、控制及各状态关系足以决定建模路径；可选产品定义帮助记录。先查Host视觉能力提示，缺失或路由变化时用`houdini_query(capabilities="visual")`补查。模型能力元数据不证明渲染或识图成功，受限时在投入大量视觉细化前说明。
2. **骨架门**：只建 anchor/中心线/代理体，先验证比例、轮廓和关系，未通过不加装饰。
3. **模块门**：把当前关键模块作为局部交付物，验证输入/输出、内部几何、属性、cook、细节与参数响应；聚焦与交接的唯一流程见[模块合同](module-quality-contracts.md#模块聚焦与交接)。
4. **集成门**：先核对必需部件在最终输出中的成员与基数，再按关系清单检查实际实例的连接、包含、间隙、禁止相交和 warning；局部通过与集成通过分开，非退化统计只是其中一项。
5. **视觉门**：声明资产轴向，整体验轮廓，局部特写验小部件与连接；有外部参考时使用可比较视角。
   先用 `render_view.check`/`render_check` 拒绝近黑、空白、目标缺失或裁切图片，再做语义读图。
   首次语义读图先记录缺陷与不确定项，再决定修订或降级，不以“可辨认”代替质量通过。
6. **扰动门**：改变至少一个关键用户控制，重跑受影响模块和关系门，证明资产不是只在默认值成立。
   恢复交付值后再 cook 和复验，避免把测试状态留给用户。
7. **交付门**：最后一次几何修改后重新采集统计、warning、关系证据和交付视图，read完整产品覆盖并逐项对照原来源；只陈述有证据的完成度，区分工具实测、视觉观察、失败和未验证，并列出外部真实性、审美和简化边界。Host只能提醒已声明义务，漏声明的必需项仍由作者对照来源发现。

## 边界与反例

- 风格化或抽象任务可以由用户授权 agent 自选比例；仍要把该选择写成风格假设，而非真实规格。
- 低 LOD 允许省略内部机械结构，但不能破坏用户要求的轮廓、连接或运动语义。
- 用户说“你决定”不等于无需合同；agent 可以自行选择，但要披露选择和完成门。
- 更多节点、更多 primitives、无 cook warning 或能渲染，都不是“细节丰富/高质量”的充分证据。
- todo 完成、旧截图或修改前的点数不能证明最终状态；最后一次 mutation 会使依赖它的旧证据失效。
