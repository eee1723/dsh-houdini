## 1. 证据等级

| 等级 | 典型证据 | 允许动作 |
|---|---|---|
| E0 线索 | 模型记忆、搜索摘要、未打开页面、转述 | 只用于寻找来源，不写规范 |
| E1 单例 | 一个 trace、一个视频、一个工程、一次实验 | 建 observation/candidate，修确定性当前产物问题 |
| E2 复核 | 两个独立任务，或 SideFX 官方资料 + 目标版本本机复现 | 可采纳普通 domain 规则/P1 设计 |
| E3 稳定 | 三个以上多样任务、跨版本验证、反例分析 | 可形成强规则、拆并或弃用建议 |

可复现的 P0 工具 bug、状态污染、数据破坏或虚假成功不必等待多个任务，但必须有回归。
来源权威性和泛化强度是两条轴：官方文档可权威说明 API，却未必证明它适用于所有任务。

## 2. 通用吸收流程

对每个输入材料：

1. 记录来源、作者/所有者、时间、Houdini 版本、许可/隐私、原始路径或 URL。
2. 分离事实、作者选择、推断、审美偏好和未知项。
3. 提取会改变 agent 决策的 claim，而不是摘要全部内容。
4. 为 claim 写适用条件、反例、目标层和验证办法。
5. 查现有 skills/known patterns；选择追加证据、窄修正、候选新 skill 或 NO_CHANGE。
6. 用官方资料/本机 runtime/另一任务做三角验证。
7. 只把抽象规律写入 skill；原始材料留在其合法位置，不复制大型内容进包。

## 3. Trace

先用 `houdini-trace-analysis` 的确定性 evidence 和量表。每个 skill delta 引用 session、步骤、
用户契约和 capability snapshot，并区分：

- agent 未加载/未遵守已有 skill；
- skill 指令缺失或错误；
- 工具缺失/缺陷；
- 任务专有设计错误；
- 完成门不足；
- 最终交付文本夸大。

一次采用失败不自动说明 skill 内容错误，也可能是 description/dispatch、旧 session catalog、
模型能力或工具执行缺口。先修正确层。

如果用户只要求分析 trace，输出 delta proposal，不修改生产 skill；用户明确要求更新/修复后，
再加载本治理 skill执行变更。

## 4. SideFX 官方资料与本机版本

优先级：

```text
目标版本实际 runtime/Tab/节点结果
↔ 同版本 $HFS/houdini/help、shipped shelf/Python source
↔ SideFX 官方在线 docs/learning path
→ 第三方资料
```

在线文档必须打开原页，不用搜索摘要当证据。记录页面对应的 Houdini 版本；当在线最新文档
与本机版本不同，以本机行为决定当前工具契约，同时在 skill 标注版本差异。

不要复制文档。提炼：系统解决的意图、输入/输出数据、关键初始化、适用边界、失败模式、
最小验证。节点名通过运行时 Tab 发现，除非稳定性已跨版本验证，否则不写死版本后缀。

官方资料可反复复查：Houdini major/minor 升级、trace 出现旧节点/隐藏 tool、domain skill 的
关键 claim 超过一个主要版本未复验时触发 source refresh。

## 5. 视频

视频是高上下文示范，不是自动权威来源。

1. 确认用户有权提供/让系统分析；记录 URL/文件、作者、发布日期、软件版本和时间戳。
2. 有视频下载/转录 skill 时按其权限与来源流程使用；否则要求已有 transcript/关键时间戳，
   不为吸收知识擅自调用收费服务或绕过访问限制。
3. 把讲解拆成 claim + timestamp + 可见操作/结果；区分作者偏好与 Houdini 不变量。
4. 不把长转录、字幕、画面或作者代码复制进 bundled skill；使用短摘要和来源链接。
5. 第三方视频默认 E1。需要 SideFX 文档、本机复现或第二独立来源才能升级为强规则。
6. 若视频与 runtime 冲突，保留冲突和版本上下文，不用多数投票覆盖实测。

适合吸收：不明显的工作流顺序、UI tool 初始化、输入输出契约、验证技巧、常见失败模式。
不适合直接吸收：个人快捷键、工作室私有命名、审美偏好、未经解释的“永远这样做”。

## 6. HIP/HDA/工程

工程分析必须只读优先：

- 在副本/disposable session 中打开，未经明确授权不保存原 HIP、不升级资产、不改外部 HDA 库；
- 记录 Houdini 版本、上下文、节点类型/version、DAG、参数差异、表达式/引用、属性契约、
  time dependency、cook warning/error、缓存/外部依赖、显示/渲染输出；
- 对 HDA 区分公开接口和内部专有实现；对缺失资产/插件明确不可判定；
- 将 project-specific architecture 与 domain invariant 分开；
- 性能结论需要 cook/performance evidence，不能由节点数猜测；
- 专有代码、商业 HDA、绝对路径、用户名、资产内容和密钥不得进入 bundled skill。

项目分析本身可发展为独立 `houdini-project-analysis` skill，但要先有重复任务、稳定只读契约、
依赖/隐私边界和完成门；治理 skill 只负责准入，不承担深度工程审计的全部步骤。

## 7. 冲突、隐私与版权

- 用户授权分析不自动授权公开、再分发或长期保存完整材料。
- 来源含个人/客户/工作室信息时，skill 只写匿名抽象规律；原始证据路径不进入公开包。
- 第三方代码或长文本遵守许可和引用限制；优先自己描述原理，不做近似复制。
- 多来源冲突时按版本、实际 context 和可复现性组织，不用“官方/视频/工程谁更高级”简单覆盖。
- 变更说明列出未采纳 claim 及理由，防止下一轮再次无上下文引入。
