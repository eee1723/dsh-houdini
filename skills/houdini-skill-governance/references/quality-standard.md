# Houdini domain skill 质量规范

## 1. 质量目标

Skill补充模型缺少的领域信息，帮助选择适合任务的方法。默认模型能够理解要求、规划与调整；
不以固定能力假设把所有任务串成同一流程。

有用内容通常回答其中一个问题：

- 何时适用，何时需要不同方法？
- 哪项Houdini数据、节点或版本事实容易被误解？
- 哪种构造能改善当前编辑方式、性能或观察能力？
- 如何从实际输出判断用户关心的结果，当前检查又不能证明什么？

删除不改变判断的通用训诫、重复提示和失效协议。字数少不是唯一目标，但每段都应有实际用途。

## 提示词编排

| 层 | 回答的问题 | 不重复的内容 |
|---|---|---|
| persona | 为谁完成什么、如何权衡质量与总成本、如何判断和交付 | 节点配方、工具精确签名 |
| system guidance / 工具合同 | 哪个入口负责什么、执行与恢复的真实边界 | 领域默认建模路线 |
| domain SKILL.md | 本领域默认怎么选、何时换方法、何时读哪份资料 | 低频完整手册、重复执行限制 |
| reference / 节点卡 | 条件性方法与观察；具体节点的平台事实 | 另一份全局persona或完成账本 |

方法建议写清适用条件、默认选择和例外，区分用户指定方法、工程现状、产品偏好与执行硬边界。
默认偏好不覆盖用户要求，不因单次失败变成禁令；例外应有任务、算法或实测成本依据，不能仅以“模型擅长代码”抹掉编辑目标。
高价值决策前置：先写会改变交付、实现选择或权限范围的分岔，再给当前问题的资料入口。按需读取细节：入口只给决策与路由，详细知识保留一个维护位置。指令具体程度随风险变化：开放式方法写取舍依据，易出错的接口和权限边界写精确条件。新增规则前检查现有来源并就地替换，避免末尾追加互相竞争的补丁。

这种分层采用按需披露上下文与清楚工具职责的设计原则，见[Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
和[Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)；具体Houdini方法仍以当前接口和实际观察为准。

## 2. 方法与执行边界

### 方法自由度

开放式建模给出候选表示、权衡和有用例子，由模型选择顺序、批次和实现。简单编辑直接完成。
复杂任务可以借助DSH计划或工作区文件记录需求，不要求另填合同、固定模块数量或阶段表单。

只有偏离会造成具体执行错误、数据损坏或越权时，才写固定顺序和硬约束。例如主线程队列、
Raw Gate、节点所有权、明确输出、参数恢复和Save As授权由执行合同维护；领域skill引用相关边界，
不重复实现第二套准入门。

Houdini的常见工作习惯可作为建议：先看中间结果、共享尺寸来源、保留清楚输出、分离可替换组件、
及早观察高风险局部。这些建议不规定所有资产的节点类型、容器层次或唯一工作顺序。

### 已知方法与探索

准确的节点/参数片段放在按需reference，写清输入、输出、适用版本和局限。
已验证方法可以减少重复探测，遇到不适用的任务仍可换方法。

未知接口优先看当前公开工具说明、节点信息和实际数据；需要时使用本机帮助、最小实验或源码。
不限制固定探测层数或失败次数。重复错误应促使模型检查失败原因与信息缺口，
停止或恢复取决于实际副作用、恢复状态和用户目标。

### 观察与证据

执行事实与任务质量分开判断：cook、总bbox、文件存在或图片送达只证明各自范围。
上游driver、binding或helper成功不代替最终交付输出。数值检查不支持的方法保持未验证，
实际识图失败不能报告视觉已验证。

最后相关修改会使受影响的旧观察失效；只刷新有关检查。测量与视觉冲突时检查对象、
方法及条件，保留无法解决的不确定项，不把改测更容易的对象写成原问题通过。

### 验证与改动相称

| 改动 | 合适的检查 |
|---|---|
| 修正文案、删除过时协议或重复策略 | 对照当前实现、调用者与链接，运行相关文档/结构检查 |
| 修改触发范围、拆并skill或移动资源 | 注册、引用、打包；必要时观察实际catalog/加载行为 |
| 修改版本敏感语法、数据关系或恢复方法 | 当前支持版本中直接受影响的最小实际行为与失败路径 |
| 声称任务质量或效率提升 | 代表性任务与适用反例；泛化结论需独立任务证据 |
| 正式发布 | 按项目发行合同确认支持版本、安装、加载与真实入口 |

按具体改动选择，不能把固定七项矩阵当作所有编辑的准入条件。
已有检查通过后，仅因新改动、失败或未解决问题扩大验证。缺少行为证据时准确说明验证范围，
无需把完成的文档修正降格成另一套生命周期状态。

## 3. 新建与资源组织

新skill应有可识别的用户意图，以及不能自然放入既有skill的独立知识或资源。
目录长度、网络类型名称或“以后可能需要”本身不构成拆分理由。
已有任务已经显示独立价值时可以新建，不需要等待固定数量的案例。

Frontmatter保留稳定名称和简短、明确的description；列出必要相邻排除边界即可。
`SKILL.md`维护共同目标、关键选择和按需路由。精确schema、示例、版本差异和长资料放reference，
通过实际问题链接，不要求每个skill套同一标题或执行步骤。

对版本敏感或重要外部主张，记录来源、适用上下文、已验证范围与反例即可；
现有来源记录能表达清楚时不另填固定claim表单。过程和证据留会话/CI或临时产物，
稳定结论就地维护，待办只进入仓库handoff。

## 4. 泛化与唯一维护源

区分任务设计选择、可复用方法、Houdini平台事实和执行不变量。
个人命名、某件资产的构造顺序或一次模型失败，不自动成为通用硬规则。

同一知识优先更新已有维护位置；一般方法留领域skill，精确工具合同留工具，
维护技能不规定建模任务如何推进。需要跨层引用时只概括边界，不复制整段规则。

评测只提供证据。实例标识、对象配方、目标数值、评分rubric和答案不进入生产prompt。
原失败实例的改善可支持局部修复；只有独立任务观察才能支持相应的泛化结论，
未见任务或私有答案不用于调参。

## 5. 拆分、合并与删除

按触发意图、知识职责、维护成本和实际误路由决定拆分或合并。
如果只是文件变长，先考虑按需reference；存在独立用途时可以保留低频技能。

已失效、重复或不再服务产品目标的内容可直接删除或替换。先检查实际调用者，
同步注册、链接与资源，保留需要的执行或诊断能力；有真实消费者兼容需求时才安排迁移期。
不设置“三个任务后才能删除”或强制先弃用的数量与状态门。

## 6. 完成核对

确认本次内容有用、触发明确、可按需发现，并与当前实现及执行边界一致。
检查必要的frontmatter、引用、注册和资源，运行与改动相称的验证。
报告结果及实际验证范围，区分源码可用、运行中已加载和真实任务效果；
不以文字匹配、目录存在或计划状态证明行为质量。
