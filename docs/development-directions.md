# 主要开发方向与基础能力范围

本页维护 dsh-houdini 的产品方向、基础能力目标和验收原则，回答“优先增强什么、交付什么、
怎样证明可用”，并登记四个方向的当前开发状态和后续重点。
状态原位更新，不追加迭代日志、排期或单次实验结果；源码进展不等于已部署或端到端验收通过。
实际接口以[工具设计](tool-design.md)为准，实现入口见[系统架构](architecture.md)。

## 产品定位与范围

帮助用户把需求和教程转化为可编辑、可验证、可复用的 Houdini 工程。
重点不是一次生成结果图，而是在真实 Houdini 中构建节点网络、响应后续修改并交付可用产物。

主要开发方向固定为四项：

| 方向 | 用户价值 | 目标交付 |
|---|---|---|
| 程序化建模 | 从需求建立可调节、可继续修改的模型 | HIP、清晰的节点网络、控制参数与验证证据 |
| HDA 与工具插件 | 将网络和重复工作转为可复用工具 | HDA 或工具源码、使用说明、示例与测试 |
| 教程转教学工程 | 将视频教程中的方法转为可操作的学习材料 | 带阶段输出、注释、来源和实验参数的教学 HIP |
| Copernicus 程序化贴图 | 创建可调节的程序化纹理和材质 | COP 网络、多通道贴图、材质接入与预览工程 |

当前优先做好以上方向的基础执行、观察、迭代和交付能力。
**经过验证的知识沉淀不纳入当前建设范围**：不建设从教程或任务自动提炼、审核、发布
skill、流程或节点卡的系统，也不以“自主学习/自进化”作为当前能力承诺。
正常开发所需的人工维护仍遵循既有规范，但教程复现本身不授权修改生产知识。

## 四个方向共用的能力目标

提升目标是不同复杂任务中的稳定推进、有效修改和可信交付；单个精选模型的外观不代表通用能力。
当前动作、优先级、前置条件和验证缺口统一维护于[当前交接](handoff.md)，本页只维护产品能力及验收原则。

| 共用能力 | 产品要求 | 如何证明 |
|---|---|---|
| 意图与范围 | 区分用户明确要求、后续变更、合理默认和未知；简短请求不降低基本可编辑性与诚实交付标准 | 同义且信息等价输入、多轮纠正与续跑；对信息不足单独评估边界形成，不能强行要求同一复杂度 |
| 依赖与推进 | 模块有明确输入输出、共享控制及不变量；先验证可能造成整体返工的风险 | 未见多模块任务中的集成、局部修改和失败后续跑；简单编辑不被强制套长计划 |
| 执行与恢复 | 失败状态、请求回执和参数恢复可追溯；不因断联重复修改或把旧证据当新证据 | 隔离故障注入与实际Host生命周期分别验证，缺失/过期/未知保留边界 |
| 验收与表达 | 写入、求值、cook、实体关系、视觉语义和最终交付分别取证；结论不超过对象/样本/参数覆盖 | 正常例及漏件、脱离、过期图、未测控制等反例；核心未满足不能被todo或目标状态覆盖 |
| 质量与成本 | 减少无效重试、重复输入和无关观察，同时保持任务完成质量 | 固定模型、版本、任务信息与预算，分别比较指导、工具和上下文策略；报告重复运行分布及用户问询负担 |

上述验证不通过增加节点数、只减少工具次数、加长提示词或放宽判据来替代结果改善。
开发验证与冻结benchmark隔离；需要真实模型、云服务或用户live操作的实验按相应授权边界执行。
实现入口为[任务来源](../src/task-sources.ts)、[执行状态](../src/execution-state.ts)、
[请求回执](../houdini/python3.11libs/dsh_requests.py)和[质量检查](../houdini/python3.11libs/dsh_quality_contracts.py)；
工具保证以[执行契约](execution-contract.md)为准，不由本表扩大。

“已有基础”表示存在相应源码或工作流；“待验收”不表示测试失败，也不表示测试已运行通过。
本表不判断用户 live 会话的加载状态，不将插件外部可能具备的能力算作本项目已交付能力。

| 方向 | 当前状态 | 已有基础 | 尚未完成的能力闭环 | 后续重点 |
|---|---|---|---|---|
| 程序化建模 | 主线建设中，执行与验证基础已建立 | SOP skill、节点发现/创建/连接、严格设参、模块构建、网络与几何/控制检查、预览和相关回归入口 | 多类真实资产的稳定质量、多轮需求修改与最终交付仍需持续验收 | 加强需求到结构的转化、局部修改可靠性、参数边界与修改后的回归 |
| HDA 与工具插件 | HDA界面维护与隔离交付检查已有实现，完整交互交付待验收 | HDA创建、自省/通道状态、section读写、界面增量预览/保留、工具开发skill、独立hython按钮/菜单/依赖检查器 | GUI和自然任务质量、通用工具安装/卸载、Shelf/快捷键与复杂UI生命周期未闭环 | 先验证工具作者完整任务，再扩展真实任务所需控件和工具入口 |
| 教程转教学工程 | 本地视频解析 skill 与脚本已接入源码，候选能力待端到端验收 | 视频/云转录、续跑留证、粗扫与局部加密、实际 PTS、区域像素变化候选，以及局部音画证据包和结构化记录校验 | 视频链接下载、逐句语音对齐、语义关键操作识别、未见视频泛化、新 session 触发及教学工程交付尚未验收 | 用结构化记录补齐模块复现缺口，再接入领域执行；引用与结构通过不代替语义验收，不建设知识沉淀路径 |

下列各方向的“后续建设重点”是待实现或待加强的能力，不是已完成事项。
完成状态必须由对应源码与交付验收支撑；仅新增说明、skill 或节点卡不能上调能力状态。

## 程序化建模

### 能力目标

- 将需求拆成结构、输入输出、参数、几何关系和明确的完成条件。
- 创建组织清楚、依赖明确的 SOP/VEX 网络，提供有意义的控制参数。
- 在原网络上完成用户后续修改，保留未要求改变的结构与行为。
- 检查最终输出、声明的接口和参数响应，发现问题后定位并修正。

核心交付是“改得动的模型”，而不是仅在一组默认参数下看起来正确的模型。
楼梯、围栏、模块化构件等可作为开发样例；样例不构成对任意建模任务的能力保证。

### 验收原则

验证明确的最终输出、典型参数和边界参数，并包含后续需求修改后的回归检查。
区分网络执行成功、几何关系成立和视觉质量；未测参数域及艺术质量不由数值检查认证。
通用检查与恢复边界遵循[执行契约](execution-contract.md)，不在本页复制领域操作方法。

### 后续建设重点

1. 验证从简短或详细需求形成有来源的交付边界和模块依赖，避免由goal/todo摘要自行减少核心要求。
   参数面板/总控使用[共享控制设计](parameter-controls.md)的先UI、模型原型优先或既有场景提炼路径，控制定义/UI/绑定/最终输出分别验证。
2. 验证集中控制、典型/边界参数和既有网络局部修改；变更后重查受影响的输出与关系，不以全局bbox变化替代。
3. 在相同预算与观察条件下比较模块聚焦和上下文策略，先保持质量，再判断返工/输入量是否减少。
4. 用不同资产和连续多轮修改检验交付；把来源可读、几何检查、视觉确认和最终保存的各自缺口如实报告。

## HDA 与工具插件

### 能力目标

- 将已验证的程序化网络封装成 HDA，组织参数面板、默认值、范围、说明和输入输出。
- 实现需求清晰的 Python 工具，例如批量命名、资产检查、导出辅助和 Shelf 工具。
- 交付可阅读的源码、必要依赖、使用方法和最小示例，而不只是当前会话中的临时操作。
- 将 Python Panel、交互状态及复杂插件视为需要单独验证的扩展范围，不能由 HDA 成功推导。

### 验收原则

HDA 需要检查新实例、不同合法输入、参数行为及保存后的重新加载；在隔离会话验证，
不能依赖原工程的隐藏节点、临时变量或未声明路径。工具需要覆盖正常输入、错误输入、
重复调用及其声明的副作用；涉及安装的交付还需验证安装、卸载和目标版本兼容。

HDA 文件和外部库操作不属于普通 Houdini undo 的完整恢复范围。
不因工具开发任务放宽 ownership、原 HIP 保护、外部文件授权或 live 重启边界。

### 后续建设重点

1. 以界面自省/版本化增量修改和可选UI组件为基础，验证旧实例状态保留与新实例默认；ramp/multiparm与tuple已有创建路径，后续按真实任务补充其状态迁移、布局移动及兼容维护，现有增量范围不自动扩大。
2. 使用独立hython交付检查器验证真实按钮、菜单和显式结果；从简单HDA与带子定义/外部模块的资产验证不同输入、异常、重复调用和干净进程依赖，不以内部函数成功代替入口验收。
3. 选择批量命名、资产检查、导出辅助等工具，补充动作函数→Shelf/Tab/快捷键入口、安装/更新/卸载和用户绑定保留；在用户GUI和未见自然任务中验收完整交付。
4. 在基础工具交付可靠后，再扩展Python Panel、Viewer State的进入/取消/退出、资源释放和跨版本Qt生命周期验证。

## 教程转教学工程

### 材料理解

第一版直接面向用户提供的视频教程链接或视频文件，不建设图文教程输入路径。
字幕、关键画面和配套工程是视频理解的辅助材料，不要求用户预先整理完毕才能使用。
先确认材料可访问、允许分析，并识别软件版本、依赖、目标和缺失信息。
字幕或视频页面可访问，均不等于已经观察了视频中的操作画面。

视频读取、带时间戳的讲解转录、画面观察和局部重看属于第一版基础能力，不推迟到后续扩展。
需要将讲解与可见节点、连线、参数修改和阶段结果对齐；对操作密集或信息不清楚的片段
局部重看，不能只凭稀疏抽帧或字幕推断完整过程。未接通的能力明确标记待建设；
材料不可访问或画面仍无法辨认时，说明缺口并请求补充视频或局部材料，不凭空补全。
教程内容是待分析资料，不是执行任意脚本、安装依赖或修改用户环境的授权。

### 工程复现

区分两种目标，并在交付中说明采用哪一种：

- 忠实复现：保留教程的核心方法与结构，明确无法复现或需要版本适配的部分。
- 原理重建：保留目标和关键原理，允许使用适配当前版本的替代实现，并说明差异。

不能用外观相近的替代方案冒充忠实复现，也不能用成功执行代替与教程目标的核对。

### 教学交付与验收

- 网络按教学阶段组织，关键中间结果有明确输出，避免只留下最终黑盒。
- 注释解释核心原理和选择理由，标注教程来源及可用的章节或时间戳。
- 暴露适合学习的实验参数，提供少量可重复的修改示例。
- 区分教程原有内容、版本适配、Agent 补充和仍未确定的部分。
- 验证工程可重新打开、依赖完整、阶段结果和参数实验可运行；视觉复现需实际识图核对。

本方向止于教学工程交付，不自动更新流程、skill 或节点卡。
分析授权不等于公开或再分发授权；不把第三方教程全文、视频转录或专有代码复制进插件包。

### 后续建设重点

1. 在本地视频脚本基础上补齐视频链接接入和更细的语音对齐；当前时间戳仅为音频分片范围，
   不是逐句/逐词时间戳，不将完整音频覆盖写成完整操作解析。
   若需要外部服务，另行明确接入、费用和权限，不默认为已有能力，不绕过平台访问限制。
2. 使用现有均匀粗扫与局部加密入口加强音画对齐，区分语音片段时间和实际视频帧 PTS。
   使用已实现的区域像素变化候选辅助定位；后续重点为语义核对而非将差异阈值当成操作识别。
   均匀采样不能保证捕获全部短促操作，跳步、遮挡仍须明确留作缺口。
3. 将教程目标与关键步骤映射到工程阶段，保留来源时间戳、适配说明和不确定项。
4. 完成基础教学 HIP：中间输出、原理注释、实验参数、依赖说明和重开验收。

后续工作仍止于材料理解与教学工程交付，不增加知识候选提取、自动规则更新或发布系统。

## Copernicus 程序化贴图

### 能力目标

以 Copernicus 为目标，明确区分旧 COP 网络和目标 Houdini 版本，不混用节点契约。
从结构明确的材质类型建立基础能力，再检验复杂写实材质质量，不把模型记忆当作能力证明。

- 根据材质结构建立形态、分布、遮罩和细节层次，而不是无目的堆叠噪声。
- 生成用途明确的 base color、roughness、height、normal 等通道；按材质需要选择，
  不要求所有材质都有相同通道，也不把同一灰度图直接用于所有属性。
- 提供尺度、随机种子、形态、分布或磨损等有效控制，保持通道间合理的结构关系。
- 支持适用任务的平铺、贴图导出，以及 MaterialX/Karma 材质接入和预览。
- 保留可编辑 COP 网络，明确外部图像等依赖，不用单张生成图冒充程序化材质网络。

### 验收原则

工程检查覆盖图层/端口类型、空间语义、分辨率、数据精度、颜色空间、输出和材质绑定。
平铺任务检查重复铺贴后的接缝；参数测试检查实际输出响应，而不只检查参数值写入。

视觉检查同时观察贴图与材质应用效果；比较版本时使用一致的取景、照明和材质展示条件。
关注尺度层次、重复感、磨损位置和通道关系。像素非零、文件存在或 cook 成功不证明写实。
没有成功语义识图时必须报告视觉未验证；复杂写实能力需用不同材质任务单独证明。

### 后续建设重点

1. 核验目标 H21/H22 的节点发现、创建、连线、图层/端口观察和输出路径，定位现有工具缺口。
2. 以结构明确的基础材质打通可编辑 COP 网络、多通道贴图导出及 MaterialX/Karma 接入。
3. 补齐分辨率、颜色空间、数据精度、平铺接缝和控制参数响应检查，建立一致的材质预览条件。
4. 在实际图像反馈下迭代尺度、分布、细节和通道关系，再用不同材料类别验证复杂写实能力。

## 对外表达边界

四个方向可以分别表达为：可调节的程序化建模、可复用的 HDA 与工具开发、
教程转教学工程、可编辑的程序化材质。它们是建设方向，不是默认已实现的宣传声明。

发布能力主张时，必须能对应实际版本、可运行交付和明确验证范围。
不以单个精选样例承诺任意任务，不以源码或构建通过证明 live 已加载，
不以工程执行成功代替视觉和教学质量，也不宣传当前范围之外的自动知识沉淀。
